# 16. Messages 25, 26 and 27: short binary messages and the long-range broadcast

> **What you will learn**
> * Why ITU-R M.1371-3 (2007) added two more binary message types — 25 (single slot) and 26 (multi-slot with communication state) — next to the existing 6 and 8, and why you will almost never see them.
> * How to decode a message whose fields are *not at fixed offsets*: two flag bits after the MMSI decide whether a destination MMSI and a 16-bit application identifier are present.
> * How to find a field that sits at the *end* of a variable-length message (the 20-bit communication state of message 26) and why the data length that remains is ambiguous.
> * Message 27, the 96-bit position report designed for satellite reception: 18/17-bit longitude/latitude in 1/10 minute, whole-knot speed, whole-degree course, no time stamp.
> * How to tell a real rare message from receiver noise that happens to carry a valid checksum — and how to build a labelled synthetic example when the recordings do not contain one.
> * Language notes: returning two values from a function (tuple / `std::pair` / `(Obj, usize)` / tuple type) and reusing code across modules.

## 16.1 Where this fits

Chapter 8 covered the two original binary containers: message 6 (addressed, acknowledged by message 7) and message 8 (broadcast). Both were designed in 1998 for *application-specific messages* (ASMs) of up to 5 slots. Their fixed overhead is heavy for small payloads: message 6 spends 88 bits on header, sequence number, retransmit flag and the 16-bit application identifier before the first data bit, and message 8 spends 56 [M.1371-5 §3.4 Table 54, §3.6 Table 57]. Message 6 also obliges the receiver to answer with a message 7 acknowledgement, which costs a second slot on the air [M.1371-5 §3.4].

ITU-R M.1371-3 (2007) therefore added two lighter containers [M.1371-5 Annex 8 §3.23, §3.24]:

* **Message 25, single slot binary message** — "primarily intended for short infrequent data transmissions". At most 168 bits, so it always fits one slot. The destination MMSI (maritime mobile service identity) and the 16-bit application identifier are *optional*, each switched on by one flag bit, so a broadcast of unstructured data gets 128 data bits in a slot (versus 112 for message 8 and 80 for message 6). It is never acknowledged [M.1371-5 §3.23 Table 80, Table 81].
* **Message 26, multiple slot binary message with communications state** — the same header, up to 5 slots (1 004 data bits), and a 20-bit communication state at the *end* so that the message can be sent on a schedule with SOTDMA or ITDMA (self-organising or incremental TDMA; chapter 3), like a position report [M.1371-5 §3.24 Table 82, Table 83]. Also never acknowledged.

Message 27 arrived one edition later, in M.1371-4 (2010), for a different reason: **satellites**. A low-earth-orbit satellite sees thousands of ships at once and hears their 168-bit position reports colliding and arriving with up to ~9 ms (87 bit-times) of differential propagation delay between the nearest and the farthest ship in view; a 96-bit message leaves 72 bits of guard space inside the 256-bit slot for that delay, bit stuffing and synchronisation jitter [M.1371-5 Annex 4 §3.1 Table 22]. Message 27 is "primarily intended for long-range detection of AIS Class A and Class B 'SO' equipped vessels (typically by satellite)" and carries a compressed subset of messages 1–3 [M.1371-5 §3.25].

Who sends what, and how often:

| Message | Sent by | Access scheme | Comm. state | Interval |
|---|---|---|---|---|
| 25 | mobile or base station (not Class B "CS") | RATDMA, ITDMA, CSTDMA, FATDMA | none | unscheduled |
| 26 | mobile or base station (Class B "SO" ≤ 3 slots; not Class B "CS") | SOTDMA, RATDMA, ITDMA, FATDMA | SOTDMA or ITDMA | scheduled |
| 27 | Class A and Class B "SO" only | MSSA (multi-channel slot selection) on channels 75 and 76 | none | nominally every 3 min, alternating channels so each is used every 6 min |

Sources: [M.1371-5 Annex 8 Table 46] (priority 4 for 25/26, priority 1 for 27), [M.1371-5 Table 80, Table 82] (Class B restrictions), [M.1371-5 Annex 4 §3.2–§3.3.4] (message 27 channels and interval). The access schemes are chapter 3's random (RATDMA), incremental (ITDMA), carrier-sense (CSTDMA) and fixed (FATDMA) access TDMA.

Message 27 is *not* transmitted on AIS 1/AIS 2: it goes out on the two "long-range" channels 75 and 76 (156.775 and 156.825 MHz) as a transmit-only function, so an ordinary shore receiver tuned to the AIS channels never hears it [M.1371-5 Annex 4 §3.3, §3.3.4]. A base station can switch it off inside its coverage area with the *transmission control for long-range broadcast message* bit of message 4 (bit 138, 0 = stop, 1 = transmit) — but only if it has also defined that coverage area with a message 23 of station type 10; the control times out 3 minutes after the last message 4 [M.1371-5 Table 51; Annex 4 §3.3.3].

### Operational use

* **Message 25/26 on a bridge: nothing.** Table 42 of Annex 7 (use of VDL messages by a Class B "CS" unit) lists message 25 as "receive and process: optional" and 26 and 27 as "no" [M.1371-5 Annex 7 Table 42]. On a Class A unit the binary content is only meaningful to an application that knows the DAC/FI (designated area code and function identifier, chapter 8), and chart systems in practice ignore both.
* **Vessel traffic services (VTS) and port authorities** were the intended senders: a base station can push a short binary notice (a lock status, a berth assignment, a water level) to one ship (addressed) or everyone (broadcast) in a single slot without triggering an acknowledgement storm. In practice the regional ASM families that exist — the St. Lawrence Seaway water-level and lock messages, for example — were specified for messages 6 and 8 and stayed there [Seaway R41], which is one reason 25 and 26 never caught on.
* **Message 27 for coastal states**: long-range identification of ships outside VHF range, as a free complement to the mandatory LRIT system. The data arrives hours later through a satellite operator, not on the bridge.

### Unattended / automated uses

* **Satellite AIS (S-AIS).** Message 27 exists for machines in orbit. A satellite footprint thousands of kilometres across covers many independent SOTDMA "cells" whose slot maps are uncorrelated, so packets collide at the satellite. ITU-R Report M.2169 analyses the resulting detection probability — a function of the number of ships in view, the message length and the pass duration — and shows why a shorter message with more guard time helps [M.2169]. Satellite data products therefore list messages 1/2/3/18 *and* 27 for the same ship, with 27 giving a coarser but more reliably received position (0.1 nautical mile resolution, whole knots, whole degrees).
* **Timestamps are the receiver's job.** Message 27 has no time-stamp field (Table 84, NOTE 1); the satellite ground segment attaches the reception time. Downstream fusion software has to accept that a 27 can be up to a few minutes stale with respect to the satellite pass and that the *position latency* bit (≥ 5 s) is the only hint about sensor age [M.1371-5 Table 84].
* **Sensor telemetry squeezed into a slot.** The 2006 UNH tide-gauge experiments put water levels into message 8 because that was the only broadcast container [UNH RFC]; message 25 is the container those experiments wanted — 128 bits, no DAC/FI overhead if both ends agree on the format, no acknowledgement. Aid-to-navigation (AtoN) stations may transmit it (Table 46 says "M/B"), so a buoy can report battery voltage, light status or a met/hydro sample in a quarter of the air time a message 8 would need [IALA R0126].
* **Encrypted and proprietary payloads.** Because the *binary data flag* can turn the application identifier off, message 25 is a legal way to broadcast bits that no public specification describes. The one real message 25 in our recordings (§16.5) is exactly that: unstructured, from an all-ones MMSI, repeating every six minutes. Treat such traffic as opaque; do not try to guess.
* **Anomaly detection.** The rules above are checkable by a program: a message 27 on channel A or B, a 27 whose repeat indicator is not 3, a 25 longer than 168 bits, a 26 whose MMSI belongs to a Class B "CS" unit, or a 27 from an MMSI that is not a ship (MID rules in [M.585-9]) are all flags for either a non-compliant transmitter or a spoofer replaying satellite data on VHF.
* **Noise masquerading as rare types.** Any receiver occasionally passes a CRC-valid burst of noise. Because 25, 26 and 27 are rare, a disproportionate share of what a log *labels* as 25/26/27 is garbage (§16.6). Data-mining pipelines that count message types must validate lengths and field ranges first or they will "discover" long-range broadcasts in a New Hampshire estuary.

## 16.2 The specification

### Messages 25 and 26: the shared header

Both messages start with the same 40 bits, then two optional blocks [M.1371-5 §3.23 Table 80; §3.24 Table 82]:

| Bits | Len | Field | Type/units | Not-available | Notes |
|---|---|---|---|---|---|
| 0–5 | 6 | Message ID | uint | — | 25 or 26 [Table 80/82] |
| 6–7 | 2 | Repeat indicator | uint | — | 0 default, 3 = do not repeat [Table 80/82] |
| 8–37 | 30 | Source ID | MMSI | — | [Table 80/82] |
| 38 | 1 | Destination indicator | flag | — | 0 = broadcast, 1 = addressed [Table 80/82] |
| 39 | 1 | Binary data flag | flag | — | 0 = unstructured, 1 = 16-bit application identifier follows [Table 80/82] |
| 40–69 | 30 | Destination ID | MMSI | — | **only if bit 38 = 1** [Table 80/82] |
| 70–71 | 2 | Spare | uint | — | **only if bit 38 = 1**, "for byte alignment" [Table 80/82] |
| *next* | 16 | Application identifier | DAC (10) + FI (6) | — | **only if bit 39 = 1** [Table 80/82; Annex 5 §1.1] |
| *rest* | n | Binary data | bits | — | see the length tables below |

So the first data bit is at offset 40, 56, 72 or 88 depending on the two flags. Message 24 (chapter 14) already chose between two layouts on a part-number field; here the *offsets themselves* move with earlier field values — [Toils] calls it "a minor design defect", and it is why our decoder computes an `offset` variable instead of using literal bit positions.

The *application identifier* is the same DAC/FI pair as in messages 6 and 8: a 10-bit **designated area code** (0 = test, 1–9 international, ≥ 10 regional, by convention the sender's maritime identification digits) and a 6-bit **function identifier** [M.1371-5 Annex 5 §1.2]. Everything after it is defined by whoever owns that DAC/FI, not by M.1371.

### Message 25: length limits

Message 25 has no trailing fields: the data runs to the end of the payload. The only rule is that the whole message must fit one slot [M.1371-5 Table 80]. Table 81 spells out the maximum data bits:

| Destination indicator | Binary data flag | Max data bits | Total |
|---|---|---|---|
| 0 (broadcast) | 0 (unstructured) | 128 | 168 |
| 0 | 1 (DAC/FI) | 112 | 168 |
| 1 (addressed) | 0 | 96 | 168 |
| 1 | 1 | 80 | 168 |

[M.1371-5 §3.23 Table 81]. Class B "CS" stations should not transmit it, and it "should not be acknowledged by either Message 7 or 13" [M.1371-5 §3.23].

### Message 26: data, spare, and the trailing communication state

After the header and data, message 26 ends with [M.1371-5 §3.24 Table 82]:

| Position | Len | Field | Notes |
|---|---|---|---|
| after data | 4 | Spare | "Needed for byte alignment" [Table 82] |
| last 20 bits | 1 | Communication state selector flag | 0 = SOTDMA state follows, 1 = ITDMA state follows [Table 82] |
| | 19 | Communication state | SOTDMA [Annex 2 §3.3.7.2.2 Tables 18/19] or ITDMA [Annex 2 §3.3.7.3.2 Table 20] — the same two 19-bit structures as messages 1–3 |

Table 83 gives the data maxima per slot count:

| Dest. ind. | Bin. flag | 1 slot | 2 slots | 3 slots | 4 slots | 5 slots |
|---|---|---|---|---|---|---|
| 0 | 0 | 104 | 328 | 552 | 776 | 1000 |
| 0 | 1 | 88 | 312 | 536 | 760 | 984 |
| 1 | 0 | 72 | 296 | 520 | 744 | 968 |
| 1 | 1 | 56 | 280 | 504 | 728 | 952 |

[M.1371-5 §3.24 Table 83]. Check the arithmetic for the first row: 40 header + 104 data + 4 spare + 20 comm state = 168, one slot; each further slot adds 224 bits ("allows for 32 bits of bit-stuffing") [Table 82]. Up to 3 slots normally, 5 with FATDMA reservations; Class B "SO" at most 3; Class B "CS" none [Table 82].

**The padding ambiguity.** A receiver sees only the total bit count *N*. It knows the comm state is the last 20 bits, so the data (plus spare) is *N* − 20 − header bits long. But it cannot tell where the data stops and the 4-bit spare starts, because a sender that follows Table 83 sends data lengths that are multiples of 8 plus 4 spare, while a sender with 60 bits of data may send 60 + 4, or 64 + 4, or 60 + 0 — and the VHF data link then pads the frame to a byte boundary with zeros that the receiving unit may or may not strip before it emits the `!AIVDM` sentence [M.1371-5 Annex 2 §3.3.7 ("unused bits in the last byte should be set to zero"); Toils]. Our decoder reports everything between the header and the comm state as `data` and gives you `data_bits`; if `data_bits % 8 == 4` the last four bits are very probably the Table 82 spare. There is no rule that makes this certain, and message 8 payloads (chapter 8) suffer from the same trailing-padding uncertainty.

### Message 27

Fixed 96 bits [M.1371-5 §3.25 Table 84]:

| Bits | Len | Field | Type/units | Not-available | Notes |
|---|---|---|---|---|---|
| 0–5 | 6 | Message ID | uint | — | 27 [Table 84] |
| 6–7 | 2 | Repeat indicator | uint | — | "Always 3" [Table 84] |
| 8–37 | 30 | User ID | MMSI | — | [Table 84] |
| 38 | 1 | Position accuracy | flag | 0 | 1 = high (≤ 10 m), as message 1 [Table 84; Table 48] |
| 39 | 1 | RAIM flag | flag | 0 | receiver autonomous integrity monitoring, as message 1 [Table 84] |
| 40–43 | 4 | Navigational status | enum | 15 | same 16 values as message 1 [Table 84; Table 48] |
| 44–61 | 18 | Longitude | signed, 1/10 min | 181° = 0x1A838 | East positive; the sentinel also means "position older than 6 hours" [Table 84] |
| 62–78 | 17 | Latitude | signed, 1/10 min | 91° = 0xD548 | North positive; same 6-hour rule [Table 84] |
| 79–84 | 6 | SOG (speed over ground) | knots, 0–62 | 63 | whole knots [Table 84] |
| 85–93 | 9 | COG (course over ground) | degrees, 0–359 | 511 | whole degrees [Table 84] |
| 94 | 1 | Position latency | flag | 1 | 0 = reported position is < 5 s old, 1 = > 5 s (default) [Table 84] |
| 95 | 1 | Spare | — | 0 | "to preserve byte boundaries" [Table 84] |

Points to notice:

* **Longitude and latitude are 18 and 17 bits, not 28 and 27.** The unit is 1/10 *minute*, so you divide by 600 to get degrees (messages 1–3 divide by 600 000). The resolution is 0.1 nautical mile in latitude. The not-available sentinels are still 181° and 91°, which in these widths are 181 × 600 = 108 600 = 0x1A838 and 91 × 600 = 54 600 = 0xD548 [Table 84].
* **Speed and course are whole numbers.** 6 bits give 0–62 knots with 63 as not available; 9 bits give 0–359° with 511 as not available [Table 84]. A speed of 62 means "62 or more".
* **There is no time stamp.** "The receiving system is expected to provide the time stamp when this message is received" [Table 84 NOTE 1].
* **Bit 94 changed its name.** M.1371-4 called it *status of current GNSS position* (0 = current GNSS position, 1 = not current = default); M.1371-5 renamed it *position latency* with the 5-second threshold. The bit means the same thing [M.1371-5 Table 84]. We output `position_latency`.
* Navigational status table (identical to Table 48, reproduced so this chapter stands alone): 0 under way using engine, 1 at anchor, 2 not under command, 3 restricted manoeuvrability, 4 constrained by her draught, 5 moored, 6 aground, 7 engaged in fishing, 8 under way sailing, 9 reserved for HSC, 10 reserved for WIG, 11 power-driven vessel towing astern, 12 power-driven vessel pushing ahead or towing alongside, 13 reserved for future use, 14 AIS-SART/MOB-AIS/EPIRB-AIS active, 15 undefined (default) [M.1371-5 Table 48].

## 16.3 Decoding one message by hand

### A recorded message 25

The only structurally valid message 25 in all of our recordings is one payload, received five times between 20:22 and 20:46 UTC on 26 May 2011 by the UNH Coastal Marine Lab receiver (`nhcml`), about six minutes apart: `sample-data/tide3/ais/ais-2011-05-26` lines 1648, 1650, 1654, 1656 and 1661. Two of them are lines 4 and 5 of [`data/ch16-messages-25-26-27.nmea`](../data/ch16-messages-25-26-27.nmea):

```text
!AIVDM,1,1,,A,I?wwwwhHS>0fgGQ0UImCTdkfB=>R,0*16,rnhcml,1306441349.52
```

28 characters, 0 fill bits → 168 bits, exactly one slot. The six-bit groups (Appendix B gives the table):

```text
I      ?      w      w      w      w      h      H      S      >      0      f      g      G
011001 001111 111111 111111 111111 111111 110000 011000 100011 001110 000000 101110 101111 010111

Q      0      U      I      m      C      T      d      k      f      B      =      >      R
100001 000000 100101 011001 110101 010011 100100 101100 110011 101110 010010 001101 001110 100010
```

| Bits | Value | Field |
|---|---|---|
| 0–5 | `011001` = 25 | message ID |
| 6–7 | `00` = 0 | repeat indicator |
| 8–37 | `1111 111111 111111 111111 111111 11` = 2³⁰ − 1 = **1 073 741 823** | source MMSI — every bit set, not a legal MMSI [M.585-9] |
| 38 | `0` | destination indicator → broadcast, no destination ID |
| 39 | `0` | binary data flag → unstructured, no DAC/FI |
| 40–167 | `000110001000…` | 128 bits of data: the maximum for this flag combination [Table 81] |

That is the whole decode: a broadcast of 128 opaque bits from a transmitter that has not been given an MMSI. If you *were* to read the first 16 data bits as DAC/FI you would get `0001100010` = 98 and `001100` = 12, but the flag says not to, and a DAC of 98 belongs to no administration. The six-minute cadence on channel A only, and the identical payload each time, suggest a bench test or a misconfigured unit near New Castle, NH. We cannot say more — and that is the honest result for most message 25 traffic you will meet.

### A synthetic message 27

No message 27 in the recordings passes validation (§16.6), which is expected: our receivers listened on AIS 1/AIS 2, and message 27 is transmitted only on channels 75/76 [M.1371-5 Annex 4 §3.3.4]. So we built one by hand. The field values, chosen to look like a coaster leaving Boston:

| Field | Value | Bits |
|---|---|---|
| message ID | 27 | `011011` |
| repeat indicator | 3 ("always 3") | `11` |
| MMSI | 338123456 | `010100010011010101101011000000` |
| position accuracy | 1 | `1` |
| RAIM | 0 | `0` |
| nav status | 0, under way using engine | `0000` |
| longitude | −70.6° → −70.6 × 600 = −42 360 → 2¹⁸ − 42 360 = 219 784 | `110101101010001000` |
| latitude | 42.35° → 42.35 × 600 = 25 410 | `00110001101000010` |
| SOG | 12 kn | `001100` |
| COG | 95° | `001011111` |
| position latency | 0 (< 5 s) | `0` |
| spare | 0 | `0` |

Concatenated, that is 96 bits = 16 characters with no fill bits. Six bits at a time, add 48, and add 8 more if the result is above 87 (the inverse of chapter 2's armour table):

```text
K      m      2      M      J      h      8      =      J      R      3      6      Q      6      5      t
011011 110101 000010 011101 011010 110000 001000 001101 011010 100010 000011 000110 100001 000110 000101 111100
```

The sentence body is `AIVDM,1,1,,A,Km2MJh8=JR36Q65t,0`; XOR-ing its bytes gives the checksum `63`, hence line 14 of the data file:

```text
!AIVDM,1,1,,A,Km2MJh8=JR36Q65t,0*63
```

Reading it back: bits 44–61 are `110101101010001000` = 219 784 unsigned; the first bit is 1 so subtract 2¹⁸ = 262 144 → −42 360 → −42 360 / 600 = **−70.6°**. Bits 62–78 `00110001101000010` = 25 410 → **42.35°**. Bits 79–84 `001100` = **12 kn**, bits 85–93 `001011111` = **95°**. The second synthetic 27 (line 16) sets every field to its default: nav status 15, longitude 0x1A838, latitude 0xD548, SOG 63, COG 511, latency 1.

The two synthetic message 26 sentences (lines 10 and 12) and the synthetic addressed message 25 (line 8) were built the same way; their field values are listed in the comments of the data file and in §16.5. All synthetic sentences use source MMSI 338123456 and destination 366123456 — US MIDs with obviously made-up suffixes — and DAC 0, which M.1371 reserves for testing [M.1371-5 Annex 5 §1.2].

## 16.4 The code

All three decoders are short. The interesting parts are (a) a shared header function for 25 and 26 that returns *both* the partly filled object *and* the offset where the data starts, and (b) reuse of `decode_sotdma` / `decode_itdma` / `NAV_STATUS` from the messages 1–3 module instead of copying them.

### Python

[`code/python/aistut/msg_25.py`](../code/python/aistut/msg_25.py):

```python
def decode_binary_header(bits: Bits, msg_type: int) -> tuple[dict, int]:
    """The part of messages 25 and 26 that precedes the application data.

    Returns the decoded fields and the offset of the first data bit. Raises
    DecodeError if the optional fields announced by the flags are missing.
    """
    require_bits(msg_type, len(bits), 40)
    addressed = bits.flag(38)
    structured = bits.flag(39)
    out: dict = {
        "msg_type": msg_type,
        "repeat_indicator": bits.uint(6, 2),
        "mmsi": bits.uint(8, 30),
        "addressed": addressed,      # destination indicator, bit 38
        "structured": structured,    # binary data flag, bit 39
        "dest_mmsi": None,
        "dac": None,
        "fi": None,
    }
    offset = 40
    if addressed:
        require_bits(msg_type, len(bits), offset + 32)
        out["dest_mmsi"] = bits.uint(offset, 30)
        out["spare"] = bits.uint(offset + 30, 2)
        offset += 32
    if structured:
        require_bits(msg_type, len(bits), offset + 16)
        out["dac"] = bits.uint(offset, 10)
        out["fi"] = bits.uint(offset + 10, 6)
        offset += 16
    out["data_offset"] = offset
    return out, offset


def decode(bits: Bits) -> dict:
    """Decode a message 25. Raises DecodeError if a required part is missing."""
    out, offset = decode_binary_header(bits, 25)
    # Everything after the header is application data; we cannot know its
    # internal structure, so we hand it on as a bit string (CONVENTIONS §3).
    out["data"] = bits.raw(offset, len(bits) - offset)
    out["data_bits"] = len(bits) - offset
    return out
```

Note the staged `require_bits` calls: a 60-bit message with the addressed flag set is reported as `message 25 too short: 60 bits < 72`, naming the length the *flags* demand rather than a fixed minimum.

[`code/python/aistut/msg_26.py`](../code/python/aistut/msg_26.py):

```python
from .msg_1_2_3 import decode_itdma, decode_sotdma
from .msg_25 import decode_binary_header

COMM_STATE_BITS = 20   # 1 selector bit + 19 bits of SOTDMA/ITDMA state


def decode(bits: Bits) -> dict:
    """Decode a message 26. Raises DecodeError if header or comm state is missing."""
    out, offset = decode_binary_header(bits, 26)
    # The communication state is the *last* 20 bits, whatever the data length.
    require_bits(26, len(bits), offset + COMM_STATE_BITS)
    comm_start = len(bits) - COMM_STATE_BITS
    out["data"] = bits.raw(offset, comm_start - offset)
    out["data_bits"] = comm_start - offset
    selector = bits.uint(comm_start, 1)
    out["comm_state_selector"] = selector
    if selector == 1:
        out["comm_state"] = decode_itdma(bits, comm_start + 1)
    else:
        out["comm_state"] = decode_sotdma(bits, comm_start + 1)
    return out
```

```python
        "sog_knots": sog,
        "sog_available": sog != 63,

        "cog_available": cog != 511,
```

`sog_knots` and `cog_deg` are plain integers here (the fields *are* whole knots and degrees), whereas in messages 1–3 they are `Fixed` with one decimal. `lon`/`lat` keep six decimals for consistency with every other position in the output, even though the field resolution is only 1/600° ≈ 0.001 667°.

> **Language notes (Python).** `-> tuple[dict, int]` declares that the function returns two values; `out, offset = decode_binary_header(...)` unpacks them. Everything else — `from .msg_1_2_3 import …` to reuse code from a sibling module, `None` for a missing optional value — appeared in chapters 2 and 3.

### C++

[`code/cpp/msg_25.hpp`](../code/cpp/msg_25.hpp) — the header function:

```cpp
inline std::pair<Json, std::size_t> decode_binary_header(const Bits& bits, std::int32_t msg_type) {
    require_bits(msg_type, bits.size(), 40);
    bool addressed = bits.flag(38);
    bool structured = bits.flag(39);
    Json out = Json::Object{
        {"msg_type", msg_type},
        {"repeat_indicator", bits.uint(6, 2)},
        {"mmsi", bits.uint(8, 30)},
        {"addressed", addressed},      // destination indicator, bit 38
        {"structured", structured},    // binary data flag, bit 39
        {"dest_mmsi", nullptr},
        {"dac", nullptr},
        {"fi", nullptr},
    };
    std::size_t offset = 40;
    if (addressed) {
        require_bits(msg_type, bits.size(), offset + 32);
        out["dest_mmsi"] = bits.uint(offset, 30);
        out["spare"] = bits.uint(offset + 30, 2);
        offset += 32;
    }
    if (structured) {
```

> **Language notes (C++).**
> * A function that must return two values returns a `std::pair<Json, std::size_t>`; `return {out, offset};` builds the pair from a braced list, and the caller takes it apart with a *structured binding*, `auto [out, offset] = …;`, which declares two new variables at once.
> * `constexpr` declares a typed compile-time constant. We give the two sentinels the type `std::int64_t` because they are compared with the *signed* result of `bits.sint`; a bare `0x1A838` would be an `int` and `-Wextra` would warn about the mixed comparison.
> * `bits.size() - offset` is unsigned arithmetic on `std::size_t`. If `offset` were larger than `bits.size()` the result would silently wrap to a huge number rather than go negative — which is why `require_bits` runs *first*.
> * `inline` functions in headers (`decode_binary_header`, `decode_sotdma`) can be included from several files without "multiple definition" link errors; that is how msg_26.hpp reuses msg_25.hpp and msg_1_2_3.hpp.

> **Language notes (Rust).**
> * `Result<(Obj, usize), DecodeError>` is a tuple inside a `Result`. `let (mut out, offset) = decode_binary_header(bits, 25)?;` does two things at once: `?` returns early with the error if there is one, and the tuple pattern on the left names the two values. `mut` applies only to `out`; `offset` is never changed afterwards.
> * `Json::Null` is an enum variant, the explicit counterpart of Python's `None`. Rust has no implicit null.
> * `bits.len() - offset` on `usize` values would *panic* in a debug build if it went negative (and wrap in release). The preceding `require_bits(...)?` guarantees it cannot.
> * `pub const COMM_STATE_BITS: usize = 20;` is a typed constant that is inlined at each use. `const` items must have an explicit type.
> * `crate::msg_25::decode_binary_header` is how one module reaches a function in a sibling module: paths start from the crate root. Each message module is reusable without copying.

## 16.6 Pitfalls and real-world deviations

* **Expect noise, not messages.** Across every recording in `sample-data/` (roughly 2006–2011, five receivers), the scan behind this chapter found 112 `!AIVDM` lines whose first six bits say 25, 26 or 27. Exactly one payload — the 168-bit all-ones-MMSI broadcast above — survives validation. Everything else fails one of: length (32–88 bit fragments; a 240-bit "message 26" whose data would be 180 bits, not a multiple of 8; 120-, 208- and 216-bit "message 27s"), field range (COG 449), geography (positions thousands of miles from the receiver), or chronology (message 27 "heard" in 2007). Most come from the `nhjel` receiver, which emitted checksummed garbage routinely, but the USCG N-AIS feed contributes some too — at −120 to −129 dBm, i.e. at the noise floor. [AIVDM] made the same observation in 2011: "Type 25 is extremely rare… not observed even in long-duration samples from AISHub".
* **Validate before you believe.** For message 25: `payload_bits ≤ 168`, and the flags' minimum length (40/56/72/88). For message 26: at least header + 20, and ideally `(payload_bits − 40) % 8 == 0` (that is what Table 83 lengths produce). For message 27: *exactly* 96 bits, repeat indicator 3, nav status not 9–13 for a ship, COG < 360 or 511, SOG ≤ 63, and a position within a few hundred nautical miles of the receiver (or, for satellite data, on the sea).
* **Message 27 on the wrong channel.** A shore receiver tuned to AIS 1/AIS 2 should *never* hear a message 27 [M.1371-5 Annex 4 §3.3.4]. If your feed shows channel `A`/`B` message 27s with sane content, either the source is a satellite data product re-wrapped as `!AIVDM` (common; check for a TAG block or USCG `s`/`d` fields naming a satellite station), or a transmitter is misbehaving.
* **168-bit message 27s.** [AIVDM] reports message 27 payloads "sometimes transmitted with 168 bits (a full slot)" in the wild, and recommends decoding the first 96 bits with a warning. Our decoder does that; `payload_bits` in the surrounding object is your warning.
* **The 4-bit spare in message 26 is invisible.** As explained in §16.2, the sender's spare and any byte-alignment padding are indistinguishable from data at the receiver. If you implement an application on top of message 26, define the data length *inside* the application payload (as the IMO ASMs do) rather than inferring it from the message length.
* **`data_offset` is a service to the next layer.** Decoders of ASM payloads (chapter 9) take the `data` bit string; for messages 25/26 the same DAC/FI dispatch applies when `structured` is true, with the data starting at bit 0 of `data`. When `structured` is false there is no standard way to know the format.
* **The all-ones MMSI.** 1 073 741 823 is what you get from 30 unset-then-inverted bits — a factory default, or a unit whose MMSI was never programmed. It also appears in other message types from broken installations; it is a useful filter key in any pipeline.
* **M.1371-4 versus M.1371-5 wording.** Table numbers moved between editions (message 25 is Table 77 in M.1371-4 and Table 80 in M.1371-5; message 27 is Table 81 and Table 84 respectively), and bit 94 of message 27 was renamed from "status of current GNSS position" to "position latency". If a colleague's decoder calls the field `gnss`, that is why [M.1371-5 Table 84; AIVDM "Type 27"].
